# Domain Knowledge

Business domain understanding for MUSUBI (ITG fork): the vocabulary of Specification Driven
Development (SDD) as this tool defines it. `steering/product.md` summarises the product; this
file is the glossary and the rules the agents apply.

## Core Concepts

- **Specification Driven Development (SDD)**: every feature or change starts from written
  artifacts (requirements, design, tasks) that an AI coding agent executes and a human reviews.
  The artifacts live under `storage/`, versioned with the code.
- **Steering (project memory)**: `steering/structure.md` (architecture), `tech.md` (stack),
  `product.md` (business context), `project.yml` (machine-readable configuration and the
  constitution profile), `rules/` (constitution, workflow, EARS guide, gates), `templates/`
  (artifact templates) and `memories/` (this directory). Every skill reads steering before it
  acts (Article VI); steering changes need approval (VI-6).
- **Constitution**: nine articles in `steering/rules/constitution.md`, each stated as EARS
  requirements with IDs. Levels `critical` or `advisory` per article come from the project
  profile and `steering/rules/constitution-levels.yml`; `constitution.levels` in `project.yml`
  overrides them.
- **Project profile**: `library`, `cli` or `application` (P-1), declared with `core_paths`,
  `delivery_paths` and `adapter_paths`. MUSUBI itself is `cli` with core `src/` and delivery
  `bin/`.
- **Phase -1 Gate**: the approval Articles VII (Simplicity) and VIII (Anti-Abstraction) require
  before a fourth project or a wrapper around a framework. Requests use
  `steering/templates/phase-minus-one-gate-request.md`; exceptions are tracked in
  `steering/complexity-tracking.md` with a sunset date.
- **EARS requirement**: Easy Approach to Requirements Syntax. Five patterns: ubiquitous
  ("The system SHALL …"), event-driven ("WHEN … the system SHALL …"), state-driven ("WHILE …"),
  unwanted behaviour ("IF … THEN the system SHALL …") and optional ("WHERE …"). Each has a stable
  ID `REQ-<AREA>-NNN` that the traceability matrix follows (Articles IV and V).
- **Design**: C4 diagrams at context, container and component level plus Architecture Decision
  Records (ADRs), checked against Articles I, II, VII and VIII (`reviewGate.design`).
- **Tasks**: the implementation plan, with P-labels marking tasks that can run in parallel and
  task IDs `IMP-<n>.<m>-NNN` matched by `traceability.patterns`.
- **Traceability matrix**: requirement → design → task → code → test, generated by `musubi-trace`
  into `storage/traceability/matrix.yml`; `musubi-gaps` reports orphaned requirements and untested
  code.
- **Delta specification / change record**: the brownfield unit of work. A proposal
  `CHANGE-NNN` lists ADDED, MODIFIED and REMOVED requirements, affected components and risks;
  its status moves proposed → approved → implemented → archived (`storage/changes/change-log.md`).
- **Workflow and modes**: the stages in `steering/rules/workflow.md` (spike, research,
  requirements, design, tasks, implementation, code review, testing, deployment, monitoring,
  retrospective). `workflow-modes.yml` defines `small` (hours), `medium` (days) and `large`
  (a week or more) with the stages each requires.
- **Skills and agents**: 25 specialist skills (requirements analyst, system architect, software
  developer, test engineer, constitution enforcer, traceability auditor, change impact analyzer,
  steering, code references, …) plus the orchestrator with its built-in skills; 27 in the
  README's count. Installed per platform from `src/templates/`.
- **Platforms**: Claude Code (skills and `/sdd-*` commands), GitHub Copilot (`.github/prompts/`,
  AGENTS.md), Cursor, Gemini CLI (TOML commands, GEMINI.md), Codex CLI, Qwen Code, Windsurf.
- **Code index**: the SCIP index under `.scip/`, one file per language, queried with
  `musubi-code`. The grep guard (`musubi-code hint --hook`) denies a bare-name grep for an indexed
  name and points to `refs`; a quoted name searches text.
- **Review gates**: `reviewGate` in `project.yml`: EARS check, stakeholder coverage and
  acceptance criteria for requirements; C4 levels, ADRs and articles for design; coverage and
  strict lint for implementation.

## Domain Rules

1. Steering is read before any decision and changed only after approval (Article VI, VI-6);
   `/sdd-steering` (Sync) follows every change to architecture, dependencies or product.
2. Every requirement is in EARS form with a stable ID, and every ID traces to design, task, code
   and test (Articles IV, V); gaps block validation.
3. Tests come before implementation (Article III) and integration tests use real services
   (Article IX); mocks are the exception and are justified.
4. The architecture stays within three projects and uses frameworks directly; anything else needs
   a Phase -1 gate (Articles VII, VIII).
5. Changes to an existing system go through a change record: proposal, approval, apply,
   implementation report, archive; the proposal states which facts came from the code index and
   which from grep.
6. MUSUBI is English only (CHANGE-002); `tests/language-policy.test.js` enforces it.
7. The fork is installed from GitHub, never through `npx` or the registry; every change that
   reaches installed users bumps `-itg.N` and gets a `CHANGELOG.md` entry.
8. Symbol questions (does X exist, where is it defined, who uses it) go to `musubi-code` before
   grep, also inside the SDD commands.

## Terminology

| Term                    | Definition                                                                                                  |
| ----------------------- | ----------------------------------------------------------------------------------------------------------- |
| Steering                | Project memory under `steering/`; Article VI                                                                |
| Article                 | One of the nine constitutional articles (I Testable Core, II Automation Interface, III Test-First, IV EARS, V Traceability, VI Project Memory, VII Simplicity Gate, VIII Anti-Abstraction Gate, IX Integration-First Testing) |
| Level                   | `critical` (blocks) or `advisory` (warns) enforcement of an article                                         |
| Profile                 | `library`, `cli` or `application`; decides how Articles I and II apply                                      |
| Core / delivery / adapter path | Where feature logic, entry points and request-context code live                                      |
| Phase -1 Gate           | Pre-implementation approval for Articles VII and VIII                                                       |
| EARS                    | Requirement syntax with five patterns                                                                       |
| REQ-<AREA>-NNN          | Requirement ID; `IMP-<n>.<m>-NNN` task ID; `CHANGE-NNN` change ID; `GATE-<date>-NNN` gate exception        |
| Delta spec              | ADDED, MODIFIED, REMOVED requirement sections of a change proposal                                          |
| Change record           | `CHANGE-NNN.md` proposal, `-implementation.md`, `-archive.md`, `-delta.json`, archive README                |
| Change log              | `storage/changes/change-log.md`: one row per change with status, commits and archive path                   |
| Traceability matrix     | `storage/traceability/matrix.yml`                                                                           |
| P-label                 | Parallelisation marker on tasks                                                                             |
| Workflow mode           | `small`, `medium`, `large`                                                                                  |
| Skill / agent           | Specialist instruction set per platform; the orchestrator coordinates them                                  |
| Platform                | One of the seven supported AI coding agents                                                                 |
| Code index              | SCIP index built by scip-typescript and scip-python, queried by `musubi-code`                              |
| Grep guard              | PreToolUse hook that denies bare-name greps for indexed names                                               |
| ITG version             | `<upstream base>-itg.<N>`, for example `6.3.1-itg.3`                                                        |
| Upstream                | `nahisaho/MUSUBI`, the project this fork tracks                                                             |

## Business Logic Patterns

- **Artifact lifecycle**: `storage/specs/<feature>-requirements.md` →
  `storage/design/<feature>-design.md` → `storage/tasks/<feature>-tasks.md` → code and tests →
  validation report; each stage reads the previous one and steering.
- **Change lifecycle**: `/sdd-change-init` → maintainer review → `musubi-change approve` →
  `/sdd-change-apply` (implementation commits, steering updates, implementation report) →
  archive by hand into `storage/archive/<year>/CHANGE-NNN/` → change-log row and `CHANGELOG.md`
  entry → version bump when installed users are affected.
- **Status notation**: the change log strikes through passed states
  (`~~Approved~~ → ~~Implemented~~ → Archived`).
- **Steering sync after change**: structure, tech or product updated in the same change that
  alters them (VI-5); the diff is approved before it is written (VI-6).
- **Index first, grep for text**: analysis records cite `musubi-code` for definitions,
  references and dependencies, and grep for Markdown, templates, YAML and string-keyed registries.
- **Template propagation**: a change to `src/templates/` reaches user projects only through
  `musubi init` or `musubi upgrade`; this repository refreshes its own `.claude/` copies the same
  way.
