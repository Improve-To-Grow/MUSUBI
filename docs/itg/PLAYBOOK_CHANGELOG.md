## Decision change: Node 20 as the minimum version

Node 20 is the minimum, not a pin (v2.0 required exactly 22). A project uses Node 20 or any later LTS and records the exact version in `.nvmrc`; `functions/` may run a different supported version than the app. Changed in §2.2 (Firebase Functions runtime), §3.4 (`.nvmrc`) and §8.1 (CI install). This matches the Diversity project, whose CI runs Node 22 while `functions/package.json` pins 20. Review note: Node 20 itself reached upstream end-of-life on 30 April 2026, so a new project should pin the current LTS; the minimum exists so that existing Functions packages on 20 are not deviations.

## Decision change: allowlist-aware redactor; every redaction is logged as an error (added 2026-10-14)

In v2.0 the recorder ran two silent stages: the allowlist pruned undeclared keys for registered actions, then the redactor dropped keys by substring match and scrubbed values; the only check was a manual look in logs-console for names and emails. v2.1 §9.6 makes this one allowlist-aware pass with four rules (unregistered key, key list, value pattern, limit) and changes two things. First, a key registered for an action is exempt from the key-list match for that action only, never from value scrubbing: `templateName` registered on `integration.email.sent` survives, an unregistered `templateName` is still dropped, and a registered field whose value looks like an email address is still scrubbed. The redactor's key list and value patterns are not edited per project; the per-action registration in `src/lib/logs/allowlist.ts` is the reviewed place for exceptions. Second, every redaction under any rule is reported through the runtime logger at level `error` and lands in `error_events` with the action name, key path, matched rule and request id, never the value; the redacted event is still written and the caller is never failed. The action table in `documentation/AUDIT_LOGGING.md` is generated from the registration file, and a new CI gate, `check:audit-catalogue`, fails when it is stale. Changed in the header, §3.4, §4.1, §8.1, §9.1, §9.2, §9.4, §9.6, §9.9, §18, Appendix C.3, and the checklists §11.12 and §19.3, which require zero redaction errors on staging before a release. Motivation: item A1 in _Suggested Improvements_: substring matching silently removed fields the playbook itself requires (`templateName`, `promptTokens`, …). Implementation: the redactor in `src/lib/logs` takes the registration as input and calls `logger.error` per redaction; registrations for the standard events of §9.2 ship with the required fields; `scripts/checks/check-audit-catalogue.mjs` and `npm run audit:catalogue`; a Vitest fixture feeds the standard events through the redactor and asserts that the required fields survive and no error is emitted.

Amended 2026-10-16 (from _Review Notes_ A1). Four gaps in the applied solution are closed. (1) When `NODE_ENV` is `test`, the redactor throws instead of logging, so a redaction fails the test that emits the event and is caught in the PR; "the redactor never throws" now reads "never throws outside tests". (2) A logs-console threshold alert on redaction errors in `error_events`, delivered to the project's channel, is set up in Sprint 0 for both environments, so a production redaction is not first seen at the monthly review. (3) The value pattern "long opaque base64 / hex string" starts at 40 characters, and a key named `sha256` whose value is exactly 64 hexadecimal characters is exempt from it; without the exemption every fingerprint lost its hash and logged a redaction error. (4) Fingerprints are `{ length, sha256 }`; the `preview` field is dropped, because the first characters of a prompt or message can hold a name that the redactor's shape rules do not recognise. A project that keeps a preview limits it to content that cannot contain personal data and records the decision in `steering/tech.md`. Changed in §3.4, §9.1 and §9.6.

## Decision change: account-state check on every authenticated request (added 2026-10-14)

v2.0 §11.2 required that a disabled user's session is rejected on the next request, and §11.3 that a claim change takes effect after the refresh tokens are revoked, but the only verification it specified was the stateless signature check of §2.2.1, which cannot see either: an ID token or session cookie stays valid until it expires, up to one hour. v2.1 §11.4 adds the mechanism. After signature verification, the route wrapper calls Identity Toolkit `accounts:lookup` on every authenticated request, reads `disabled` and `validSince`, and rejects with `401` when the account is disabled or missing or the token's `auth_time` predates `validSince`, emitting `auth.session.rejected` with the reason. There is no cache: the check is one Identity Toolkit round trip per request, not billed by Firebase and without any Cloudflare binding, and a disabled account or revoked session is rejected on the next request for every role. A failed lookup rejects with a retryable `503` and an `error_events` row and never falls through to an unchecked token. Changed in the header, §2.2.1 (`auth-admin.ts`), §3.4, §7.4, §11.1, §11.2, §11.4, §11.5, §11.12 and §18. Motivation: item A2 in _Suggested Improvements_, option (a). The entry was first applied the same day as option (b), a 60-second KV cache per `uid` in an `AUTH_STATE` namespace with admin-role requests on (a), and changed to (a) for every request at the playbook owner's request: the uncached lookup is the simplest option (one call, no store, no TTL) and the strictest (a disabled account or a revoked session is rejected on the next request, with no cache window), and the pattern is proven: the Diversity platform has run an uncached per-request account check since the start. Implementation: the check lives in `src/lib/firebase-rest/auth-admin.ts` and runs in the authentication step of the route wrapper; the E2E list of §7.4 requires the disabled-user and revoked-session cases.

## Decision change: bearer-only sessions, no session cookie (added 2026-10-14)

v2.0 §11.5 (v2.1 §11.4) gated server-rendered routes with a Firebase session cookie beside the ID token on API calls and set defaults of 30 minutes idle and 12 hours absolute without a mechanism for either: a Firebase session cookie has a fixed expiry chosen when it is minted, and the Identity Toolkit API mints one only from an ID token, never from an existing cookie. v2.1 §11.4 drops the cookie. The ID token in `Authorization: Bearer` is the only credential; protected pages are client-rendered shells that hold no data until an API call returns, the middleware sets headers only, and server components never identify the user. The absolute lifetime (12 hours admin, 14 days consumer) is enforced statelessly in the wrapper on `auth_time`, rejected as `auth.session.rejected` with reason `expired`. The idle timeout (30 minutes admin, none consumer) is a client control: the Firebase client signs out after the idle period without input; the server guarantees are the absolute lifetime and the account-state check. Logout is an endpoint that emits `auth.logout` and revokes the refresh tokens, after which the client signs out. Resources reached without a header (downloads, images, new tabs) use signed URLs or a client fetch. The account-state check of the previous entry runs in the wrapper only. Changed in the header, §2.2.1, §3.4, §7.4, §9.10 (post-login client events go through `fetch({ keepalive: true })` with the bearer token, since `sendBeacon` cannot carry a header), §11.2, §11.4, §11.5, §11.12 and Appendix C.1 (`SESSION_COOKIE_NAME` and `SESSION_IDLE_MINUTES` removed; `SESSION_ABSOLUTE_HOURS` and `NEXT_PUBLIC_SESSION_IDLE_MINUTES`). Motivation: item A3 in _Suggested Improvements_, and the Diversity project (`2026.07.02_Diversity/diversity`), which has run bearer-only since the start: its middleware sets CORS and security headers only, and every API call is verified from the bearer token. Alternatives considered and rejected: (1) a client-driven sliding window, the client posting a fresh ID token to re-mint the cookie: idle enforced in client code, precision between the lifetime minus the re-mint interval and the lifetime, one Identity Toolkit call per re-mint, and the API path stays uncovered unless every API call also verifies the cookie; (2) a last-seen entry per sign-in in KV: server-enforced, but rejected on merit: a KV read in the middleware and in the wrapper plus a write on every active request, a second store and a second mechanism for a control that only an unattended browser needs, and no protection against a stolen refresh token, which keeps the session active; the playbook therefore does not describe it; (3) the EBC pattern (`2026.07.10 EBS/ebc`): an unsigned, self-issued JSON cookie that the middleware rewrites with a last-activity stamp, the only form in which a middleware can slide a cookie at all, forgeable, and with the idle clock running on navigations only, so API calls continue after idle expiry; (4) a server-minted custom token exchanged for a new session cookie: two Identity Toolkit calls per re-mint, the signing key in the Worker, and a fresh `auth_time` that undoes the revocation check. Every option keeps two credentials with different lifetimes and every rule of §11 implemented twice. The bearer-only model with the uncached lookup is the choice because it is the simplest (one credential, one check, no store) and the strictest (every rule of §11 enforced on every request), and it is proven: the Diversity platform has run it since the start. The session model needs no Cloudflare KV binding; the account-state lookup of the previous entry is not billed by Firebase. Not copied from Diversity: its role and status fields in the user document with claim resync on every request (§11.2 forbids them; claims remain the only source), its per-request Firestore read of the user document (the Identity Toolkit lookup of the previous entry reads the Auth record, not a database field), and its absence of lifetime checks.

## Decision change: full IP address and user agent only on security events; `export.*` and `bulk.*` join the security bucket (added 2026-10-15)

v2.0 §9.5 required `ip_address` and `user_agent` on every event, and §9.8 claimed that rows hold only ids, so that erasure of the user profile leaves no personal data in the log store. An IP address is personal data, and a user-agent string is once it sits beside an actor id, so the claim was wrong for every bucket, and the 12- and 6-month buckets held both values raw for no forensic purpose. v2.1 makes three changes. First, the recorder reduces both fields before the event leaves the application, decided by the event's action prefix: events in the security bucket carry the full address and the raw user agent; every other event carries the address truncated to a `/24` (IPv4) or `/48` (IPv6) prefix and the user agent parsed to browser family, major version and operating system, which is what reproducing a browser-specific bug needs. Inbound webhook events keep the full source address: it is the vendor's server, not a person's device, and it is checked against the vendor's published ranges. There is no platform job that truncates later; the store never holds a full address outside the security bucket. Second, `export.*` and `bulk.*` move from the 12-month domain bucket into the 24-month security bucket: they are the actions an attacker performs after a takeover and what a breach notification is scoped on. The security bucket's prefix list is fixed by the playbook, because it now also decides the network-metadata rule; the windows stay configurable in logs-console. Third, §9.8 states the position correctly: outside the security bucket, erasure leaves no personal data in the log store; security events keep the full address and user agent for 24 months, and the privacy notice says so. Changed in the header, §9.1, §9.5, §9.7, §9.8, §9.10, §11.12, §13.2, §13.3, §15.4, §18 and Appendix B. Motivation: item A5 in _Suggested Improvements_. Not applied from that item, at the playbook owner's request: the platform job that truncates the raw address after 90 days (the reduction happens at write time, so there is nothing left to truncate) and the salted hash as an alternative to truncation (a hash only matches exactly; a `/24` prefix still shows whether an export came from the same network as the suspicious login, which is what the comparison needs). Discussed and not applied: a session key (hash of `uid` and `auth_time`) stamped on every event, which would join a domain event to its login event in the security bucket without any address comparison; left for v2.2.

## Decision change: the feature kill switch is a Firestore document; the per-environment list is a `var` (added 2026-10-15)

## Decision change: log events leave the Worker through a Cloudflare Queue and a relay Worker; Functions and scripts await the write; a log write never fails the caller (added 2026-10-17)

v2.0 §9.1 (v2.1 §9.1) stated the logging contract as "fire-and-forget on the request path": writes scheduled with `ctx.waitUntil`, failures swallowed; and §9.3 described one transport, an HMAC-signed, batched POST to log-ingest with at-most-once delivery. Two things were wrong with it. `ctx.waitUntil` is a Workers primitive; in `functions/` and in operator scripts a write that is not awaited can be killed when the handler returns, so the backup Function's `audit.*` events and the scheduled jobs' `app.*` events could silently never arrive (item A10 in _Suggested Improvements_). And at-most-once plus fire-and-forget meant that ten minutes of unreachable log-ingest dropped every audit event of that window with nothing recording the loss, which defeats `audit_log` (item A11); "batched" also promised more than a Worker can do, since a Worker cannot batch across requests without a Durable Object or a queue. v2.1 changes the contract and the transport. The contract is "a log write never fails the caller", stated per runtime: in the Worker the request's events leave in one `sendBatch` inside `ctx.waitUntil`, so the response never waits; in Firebase Functions and operator scripts the recorder's flush is awaited before the handler returns, so the write completes and the result never depends on it; in both a failed delivery is retried once, then reported to the runtime log and swallowed. The Worker transport is a Cloudflare Queue, `<app>-logs-<environment>`, bound to the application Worker as the producer `LOG_QUEUE` and consumed by `workers/log-relay/`, a small Worker in the same repository with its own `wrangler.jsonc`, named `<app>-log-relay-<environment>` and deployed by the same workflow after the application Worker. The recorder sends one message per event (a message holds at most 128 KB); the relay batches across requests (up to 50 messages, five seconds), signs and POSTs each batch to log-ingest within its cap, acknowledges on `2xx` and otherwise retries the batch with a delay that doubles from one minute to one hour, up to the Queues maximum of 100 attempts, while Queues keeps the messages for its four-day retention: an unreachable log-ingest delays events and loses none. Queues delivers at least once, so log-ingest now inserts idempotently on the event `id`, which the recorder sets at emit time (§9.5, Appendix B). Functions and scripts have no queue binding and nothing runs after they return, so they keep the direct POST, awaited, with one retry. The recorder picks its transport by what is bound: the queue binding, else `LOG_INGEST_URL` and `LOG_INGEST_SECRET` (Functions, scripts, Vitest integration runs in CI against the staging endpoint), else the console (`next dev`, unit tests). A delivery failure is the one `logger.error` that is not forwarded to `error_events`, because that row would travel the path that just failed; it stays in Cloudflare observability or Cloud Logging, and the queue backlog is visible in the Queues metrics. Two consequences follow. The application Worker no longer holds `LOG_INGEST_URL` or `LOG_INGEST_SECRET`: the relay holds them as its own `vars` and secret, pushed by the deploy job with a second secrets file, and `functions/` holds the URL in `functions/.env.<project-id>` and the secret as a Firebase Functions secret set by the Firebase job (C.1 names the reader of each block; the one table of fixed names per job is still item B3, which now also covers how a rotation of a Functions secret, bound at deploy time, reaches `functions/`). And Cloudflare Cron Triggers leave the playbook: the generated OpenNext worker exports `fetch` only and is not customized, so it has no `scheduled` handler any more than a `queue` handler, and all scheduled work runs in Firebase Functions, where the playbook already put backups and exports (neither the Diversity nor the EBC project has a Worker-side Cron Trigger). Changed in the header, §2.1 (stack table), §2.1.4, §2.2 (plan statement and hosting table), §2.2.1 (`wrangler.jsonc` contract), §2.2.2, §2.2.4 (relay Worker name), §3.4, §4.1, §7.3, §8.2.1, §9.1, §9.2, §9.3, §9.5, §9.9, §10.2, §11.5, §18, §19.4, Appendix B and Appendices C.1 and C.2. Motivation: items A10 and A11 in _Suggested Improvements_, decided in _Review Notes_ A10, A11 and the second pass of 2026-10-15; the queue is viable because ITG's Cloudflare account is on the Workers Paid plan, whose Queues quota covers the volume, and §2.2 now states the plan once. Applied differently from the suggestion: the queue carries every event from the Worker, not `audit_log` only, so there is one delivery path and the relay batches across requests. Not applied: a Durable Object as the cross-request buffer (a queue is the primitive for this and needs no state of its own); a delivery failure reported into `error_events` (it would re-enter the failed path); a dead-letter queue (four days of retention and 100 attempts cover any outage that is not itself an incident).

## Decision change: Firestore rules deny all client access; Storage rules scope client uploads and reads; Firebase Storage is the default file store; rules are tested against staging, never in an emulator (added 2026-10-18)

v2.0 §11.6 (v2.1 §11.6) made the rules "server-write-only": clients could read what the Firestore and Storage rules scoped to them. After the account-state check of §11.4 (added 2026-10-14) that was a hole: the check runs in the route wrapper only, rules evaluate the ID token without a lookup, so a disabled or revoked user kept reading through the client SDK, real-time listeners included, until the token expired, while §11.4 already said that protected pages hold no data until an API call returns (problem 1 under A2 in _Review Notes_). And §7.3 forbade the emulator while §11.6 said "tested against the staging project" without saying how; `@firebase/rules-unit-testing`, the usual harness, runs only against the emulator (item A13 in _Suggested Improvements_). v2.1 settles both. Firestore rules deny all client reads and writes: every read and write of application data goes through an API route and so through the account-state check; the `ops` collection is no exception; real-time listeners are not available by default and live updates poll an API route; a project that needs client reads records a deviation naming the readable collections and accepts up to one hour of access after a disable or revocation. Storage rules are the one place where the browser talks to Firebase directly: a client may upload to and read from the paths of its own tenant, taken from the claim, with a content-type allowlist and a size limit per path, and nothing else; the one-hour window is accepted there because a disabled user cannot reach the application to use an upload; exports and links that leave the app go through short-lived signed URLs, in-app views use the client SDK, and a `getDownloadURL` link never leaves the app. With client uploads the file store follows: Firebase Storage is the default, Cloudflare R2 only for public assets served by the Worker. Rules are tested against the staging project, which is the test sandbox, with fixed test users and real objects: one staging user per role, plus one in a second tenant for multi-tenant applications, seeded by the idempotent operator script `scripts/ops/seed-test-users` with their passwords as CI-only Secrets of the `staging` Environment; one sign-in per run with the ID tokens renewed from the refresh token after 50 minutes; everything a run writes under `ci-<run-id>` and deleted at the end, with a scheduled Function deleting what crashed runs leave behind after 24 hours; per-run users for tests that disable, revoke or change a role. The cases are fixed in §11.6: Firestore, an authenticated read and an authenticated write, both denied; Storage, an upload in the user's own tenant with an allowed type and size allowed and readable by the same tenant, an upload into another tenant, a content type outside the allowlist, an upload one byte over the limit and a read of another tenant's object each denied. Because a test against staging sees the deployed rules and not the PR's, a PR that changes `firestore.rules` or `storage.rules` is also checked by the new gate `scripts/checks/check-rules.mjs`, which sends the branch's rules files and the same cases to the Firebase Security Rules API test method with a mocked `request.auth`: no deploy, no emulator, and claim combinations no fixed user has. The emulator stays out of every project; ITG used it before and found its setup and upkeep not worth it. Changed in the header, §2.1 (stack table), §2.1.4 (CI-only credentials), §2.2 (hosting table), §2.2.1 (user creation and deletion in `auth-admin.ts`), §2.2.4, §2.3, §3.4, §4.1 (`scripts/ops/`), §7.3, §7.4, §8.1, §10.2, §11.3, §11.4, §11.6, §11.12, §18 and Appendices C.1, C.2 and C.3. Motivation: problem 1 under A2 and item A13 in _Suggested Improvements_, decided in _Review Notes_ A2 (decision on problem 1 of 2026-10-15, its second pass and the owner's later decision on Storage reads), A13 (decision of 2026-10-15 and its second pass) and the third pass (B4, C6). Applied as decided. Not applied from the A13 suggestion: the emulator exception to article IX and `@firebase/rules-unit-testing`. Not applied from the A2 proposal: the revocation check inside the rules (an extra read per client read and a copy of the auth state in the database, which §11.2 rules out) and client reads with the one-hour window as the default (it remains a recorded deviation). ## Decision change: no HTTP-triggered Firebase Function is reachable from the web; a Worker route is its only caller; CI checks the invoker (added 2026-10-19)

v2.0 described Firebase Functions as being for scheduled work; v2.1 corrected that (see the _Phrasing correction_ entry below), and §2.2.2 then said that a Function which exposes HTTP "follows the same guard, rate-limit and event rules" as a route, without a mechanism: `withApiRoute`, the guards, the rate limit, the response envelope and the automatic event exist only for `src/app/api/**/route.ts`, the CI scripts of Appendix C.3 scan only that path, and the Firebase CLI deploys a 2nd-generation `onRequest` Function with public invoker access unless `invoker: 'private'` is set. The Diversity platform's `provisioningHealth` is that case: an open HTTP Function that reports project, bucket and schedule configuration (item A16 in _Suggested Improvements_). v2.1 closes the gap without a second wrapper. No HTTP Function is reachable from the web: every one is an `onRequest` export with `invoker: 'private'`, so Cloud Run rejects a request that does not carry a Google-signed identity token of a principal with the Cloud Run Invoker role on that Function, before the handler runs. Its caller is a Worker route under the normal route contract, or an operator with `gcloud` whose own account holds the role. The route carries the guard, the rate limit, the validation, the envelope and the automatic event; it calls the Function at `FUNCTIONS_BASE_URL/<name>`, a new server-configuration key in the `vars` of `wrangler.jsonc`, with an identity token that `service-account.ts` of the Firebase REST client mints from the key it already holds, the Function URL as the audience, and it propagates `x-request-id`; the Function's URL never reaches the client. The service account of `FIREBASE_SERVICE_ACCOUNT` is granted the Cloud Run Invoker role on each private Function in both Google Cloud projects in Sprint 0; there is no new key and no new secret. `onCall` is not used, because the callable protocol adds nothing when the caller is a Worker with an identity token. Every HTTP Function emits at least one event through the Functions recorder with the propagated request id, so logs-console shows the route's event and the Function's under one request. Two CI gates enforce it: the new `scripts/checks/check-function-invokers.mjs` fails on an `onRequest` export under `functions/src/` without a literal `invoker: 'private'` and on any `onCall` export, and `scripts/checks/check-route-logging.mjs` now walks `functions/src/**` as well. A diagnostic endpoint that needs Node, such as a provisioning health check, is such a Function behind a diagnostic route, so the `404` when disabled, the owner-only guard and the audit event apply at the route, and a feature switched off closes the Function with it. Changed in the header, §2.1 (stack table), §2.2 (hosting table), §2.2.1 (`service-account.ts`), §2.2.2, §3.4, §4.1, §7.4, §8.1, §9.1, §11.5, §11.11, §11.12, §18 and Appendices C.1 and C.3. Motivation: item A16 in _Suggested Improvements_, decided in _Review Notes_ A16 (option (b), 2026-10-15), its second pass (`onRequest` only, the Invoker grant as a Sprint 0 line) and the third pass (B7: the event check belongs to `check-route-logging`, not to the invoker gate). Applied as decided. Not applied from the suggestion: the `withFunctionRoute` wrapper for a Function that must be reachable from the web (no Function is, so the route contract is implemented once), and the extension of `check-route-guards.mjs` to `functions/` (the invoker gate takes its place: a private Function has no guard of its own because its only caller has one). No retention, session or configuration default changes beyond the new server-configuration key.

## Correction: Storage rules are deployed by the Firebase job (added 2026-10-16)

§2.2.4, §3.4 and §11.6 require Storage rules in both environments in the same change, but the Firebase job of the deploy workflow (§8.2.1, Appendix C.2) deployed `functions,firestore:rules,firestore:indexes` only, so nothing deployed `storage.rules` (item A8 in _Suggested Improvements_). v2.1 adds `storage` to the `--only` list and names the path filter that triggers the job: `functions/**`, `firestore.rules`, `firestore.indexes.json`, `storage.rules` and `firebase.json`. The two §8.2.1 bullets for Functions and for rules and indexes are one bullet. A project without Firebase Storage leaves `storage` out of the list and `storage.rules` out of the filter, because `firebase deploy --only storage` fails without a Storage configuration in `firebase.json` (decision in _Review Notes_ A8). No default changes: the deploy contract catches up with rules the playbook already had.

## Phrasing correction: Firebase Functions

v2.0 described Firebase Functions as being "for scheduled work" (§2.1, §2.2, §2.2.2, §4.1). Checked against the Diversity project (`2026.07.02_Diversity/diversity`): its `functions/` holds a scheduled backup (`nightlyFirebaseBackup`, `onSchedule`) **and** an HTTP endpoint (`provisioningHealth`, `onRequest`), and its operator scripts under `scripts/` borrow `firebase-admin` from `functions/node_modules`. The enforcement gap for HTTP Functions (no route contract, no CI check) was item A16 in _Suggested Improvements_, closed by the _Decision change_ entry on private HTTP Functions above (2026-10-19).
